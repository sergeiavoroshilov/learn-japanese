# Спайк 2: распознавание с ограниченным словарём (Vosk в браузере)

Следствие из [спайка №1](./SPIKE-ASR.md): drill-режиму нужен не более
качественный ASR, а **другой класс инструмента**. Ожидаемый ответ известен
заранее, поэтому задача — не «расшифровать речь», а «выбрать из 46 известных
вариантов». Vosk (Kaldi) в WASM это умеет: декодер можно ограничить списком
слов, и тогда ответить «部屋» на へ ему просто неоткуда.

Дополнительные свойства, важные для продукта: модель работает локально —
значит нет поминутной оплаты за дрилл, который почти целиком состоит из
включённого микрофона, нет бэкенда и есть офлайн.

## Что уже проверено (до замеров с голосом)

- **Словарь модели содержит одиночные моры.** Это был главный риск: если бы
  мора не была словом в лексиконе, ограничение словарём не собралось бы.
  Проверка `graph/words.txt` модели `vosk-model-small-ja-0.22`:
  базовые — **46 из 46**, дакутэн — **25 из 25**, ёон — **30 из 33**.
- **Не хватает трёх ёон:** びゃ, ぴゃ, ぴょ. Kaldi при этом не падает и не
  ругается — просто молча не может их выдать, поэтому в режиме ограниченного
  словаря эти карточки исключаются из колоды явно
  ([vosk.ts](../apps/web/src/lib/vosk.ts)), иначе они выглядели бы как
  провал распознавания.
- **Грамматика из 46 мор принимается декодером**, распознаватель создаётся
  и живёт (проверено подачей тишины: приходит пустой partial, ошибок нет).
- **Модель отдаётся и грузится**: 47 МБ tar.gz, инициализация ~1.1 с при
  локальной раздаче (первое скачивание по сети, разумеется, дольше).

Не проверено и составляет предмет спайка: **точность и задержка на реальном
голосе** — у меня нет микрофона.

## Как устроено

- `MicSource` ([audio.ts](../apps/web/src/lib/audio.ts)) владеет одним
  микрофонным потоком: из него кормится и замер начала речи, и декодер.
  Два независимых `getUserMedia` расходились бы в оценке момента начала звука.
- `VoskRecognizer` ([vosk.ts](../apps/web/src/lib/vosk.ts)) реализует тот же
  интерфейс `DrillRecognizer`, что и отклонённый Web Speech API, поэтому дрилл,
  метрики и отчёт остались прежними и результаты сравнимы напрямую.
- Vosk декодирует речь одним непрерывным потоком, и его partial-результат
  тянет за собой хвост предыдущей карточки. Поэтому при показе новой карточки
  запоминается длина текущего partial, и оценивается только то, что сказано
  после неё.
- Переключатель **«Ограничить словарь»** оставлен намеренно: свободное
  распознавание той же моделью — это контрольная группа. Если ограниченный
  словарь бьёт свободный, значит выигрыш даёт именно сужение задачи,
  а не смена вендора.

## Как запустить

```bash
bun install
bun run fetch:model   # 48 МБ, качается один раз, в git не хранится
bun run dev
```

Открыть http://localhost:5173, выбрать движок «Vosk в браузере».
С телефона — `bun run dev:https` (нужен защищённый контекст).

## Протокол замера

Важно снять **обе** ветки, иначе непонятно, что именно помогло:

1. Vosk **с ограниченным словарём**, строгое правило, 20–40 карточек базовой каны.
2. Vosk **без ограничения** (тот же прогон) — контрольная группа.
3. Повторить с включёнными дакутэн и ёон: там больше близких по звучанию пар
   (じ/ぢ, ず/づ), и именно там ограниченный словарь может начать путать.
4. Повторить на телефоне: 48 МБ модели и WASM-декодер на мобильном железе —
   отдельный риск, и по скорости, и по памяти.

Каждый прогон — кнопка «Скопировать JSON-отчёт»; отчёты складываются
в [data/](./data/).

## Критерий

Тот же, что и в спайке №1, чтобы результаты были сравнимы:

- доля распознанных ≥ **90 %** при строгом правиле;
- медиана задержки движка ≤ **500 мс**.

Плюс два новых, специфичных для локальной модели:

- загрузка модели не делает старт сессии неприемлемо долгим (ориентир — до
  ~10 с на первом запуске, дальше из кэша браузера);
- на телефоне дрилл не тормозит и вкладка не падает по памяти.

Если ограниченный словарь проходит, а свободное распознавание — нет, вывод
спайка получается сильнее самого выбора движка: подтверждается, что задача
решается **сужением, а не мощностью**, и то же самое будет верно для любого
следующего кандидата.
