# Технический анализ и рекомендации по стеку

> Статус: черновик для обсуждения. Финальные решения помечены как
> «Рекомендация», остальное — рассмотренные альтернативы.

## Требования, которые диктуют стек

1. Работает на десктопе и телефоне → **веб-технологии, PWA**.
2. Drill-режим: распознавание одиночного слога **моментально**
   (цель: < 300–500 мс от конца произнесения до смены карточки).
3. Разговорный режим: живой диалог с минимальной задержкой → OpenAI Realtime.
4. Предпочтение по рантайму — **Bun**.

## Главная неопределённость: мгновенное распознавание в drill-режиме

Это самое рискованное место проекта, его нужно прототипировать первым.
Важно: нам **не нужен полноценный ASR**. Мы заранее знаем, какой ответ
ожидаем (чтение показанного символа), задача — «сказал ли пользователь
именно это, и как быстро». Это задача keyword spotting / forced matching,
она проще и быстрее общего распознавания.

### Вариант A — Web Speech API (встроенный в браузер)

`SpeechRecognition` с `lang: 'ja-JP'`, `continuous: true`,
`interimResults: true`; ответ сверяем с ожидаемым чтением (кана/ромадзи)
нечётким сравнением по interim-результатам.

- (+) Ноль зависимостей, бесплатно, работает в Chrome (десктоп/Android)
  и Safari (macOS/iOS).
- (+) Interim-результаты приходят быстро (~200–500 мс) — достаточно для потока.
- (−) Точность на изолированных слогах не гарантирована: движок ждёт слова,
  одиночное «ку» может распознаться как что угодно. Может помочь связка
  с ожидаемым ответом (принимаем interim, содержащий ожидаемую кану).
- (−) Chrome шлёт аудио на серверы Google; поведение различается между
  браузерами; на iOS есть ограничения по автозапуску микрофона.

### Вариант B — OpenAI Realtime API в режиме транскрипции

Стриминговая транскрипция (`gpt-4o-transcribe` / mini) через WebRTC/WebSocket,
серверный VAD, дельты транскрипции в реальном времени.

- (+) Качество распознавания японского заметно выше; единый вендор
  с разговорным режимом.
- (+) Латентность стриминга сопоставима с Web Speech API.
- (−) Платно за минуты аудио; drill-сессии — это много минут микрофона.
- (−) Нужен бэкенд для эфемерных токенов (он и так нужен разговорному режиму).

### Вариант C — локальная модель в браузере (WASM/WebGPU)

whisper.cpp (WASM), transformers.js + whisper-tiny, sherpa-onnx, Vosk
(маленькая японская модель).

- (+) Офлайн, бесплатно, приватно, нет сетевой задержки.
- (−) Whisper не стриминговый по природе — чанки дают 0.5–2 с задержки;
  на среднем телефоне может быть хуже. Sherpa-onnx (стриминговые
  zipformer-модели, есть японские) — самый перспективный из локальных.
- (−) Заметный объём загрузки модели (40–200 МБ), прогрев.

### Рекомендация по распознаванию

> **Обновлено 30.08.2026 по итогам спайка №1: вариант A отклонён.**
> На реальном прогоне — 5 % распознанных карточек (1 из 20; по строгому
> правилу 0 из 20), причём в 14 случаях движок не выдал ни одной гипотезы,
> а в 5 подставил словарные слова (へ → «部屋», き → «コーヒー»).
> Разбор и следствия: [SPIKE-ASR.md](./SPIKE-ASR.md).
>
> Главное следствие для этого документа: задача drill-режима — не
> распознавание, а **проверка заранее известного ответа**, поэтому ASR
> общего назначения (в том числе платный вариант B) выбран как класс
> инструмента неверно. Приоритет получает распознавание с **ограниченным
> словарём** (Vosk/Kaldi в WASM со списком из 46 мор) — оно же снимает
> вопросы цены и офлайна. Ниже — исходные рассуждения, оставлены как
> история решения.


Прототипировать A и B параллельно за одним интерфейсом:

```ts
interface DrillRecognizer {
  start(expected: Expected): void;      // ожидаемые чтения символа
  onMatch(cb: (r: MatchResult) => void): void; // верно/неверно + латентность
  stop(): void;
}
```

- Неделя 1: Web Speech API (вариант A) — бесплатно и без бэкенда; замерить
  реальную точность/латентность на изолированных слогах на десктопе и iPhone.
- Если точность на слогах неприемлема — вариант B как основной для drill.
- Вариант C держать как исследование для офлайна (sherpa-onnx), не для MVP.
- Отдельно от ASR: **клиентский VAD** (например, @ricky0123/vad-web) для
  точного замера латентности — момент начала/конца речи фиксируем локально,
  не дожидаясь транскрипта.

## Разговорный режим

**Рекомендация: OpenAI Realtime API (speech-to-speech), WebRTC из браузера.**

- Модель уровня `gpt-realtime`: естественный голос, перебивания,
  задержка ответа в сотни миллисекунд.
- Браузер соединяется с OpenAI напрямую по WebRTC; наш бэкенд только выдаёт
  эфемерный токен (секретный ключ API в браузер не попадает).
- Системный промпт агента: уровень ученика + список слов «на повторение»
  из SRS-базы + правило «ошибки и непонимание объясняй по-русски, затем
  возвращайся к японскому».
- После сессии: транскрипт разговора прогоняется обычной текстовой моделью
  для извлечения употреблённых/непонятых слов → запись в SRS-базу.

Проактивность (честные ограничения платформ):

- **Десктоп**: открытая вкладка/установленная PWA может сама инициировать
  разговор (звуковой сигнал + начало сессии по клику; полный автозапуск
  микрофона браузеры запрещают — нужен один клик «ответить»).
- **Телефон**: Web Push (на iOS — только для установленной на экран PWA).
  Пуш «поговорим?» → тап → разговор. Фоновый самозапуск невозможен —
  это ограничение платформ, не стека.
- Расписание пушей генерирует бэкенд (случайные моменты в разрешённых окнах).

## Рекомендуемый стек

| Слой | Выбор | Почему |
|---|---|---|
| Рантайм/пакеты | **Bun** (workspaces) | предпочтение автора; быстрые тесты `bun test` |
| Язык | TypeScript везде | общие типы карточек/SRS между клиентом и сервером |
| Фронтенд | **React + Vite + vite-plugin-pwa** | зрелая экосистема; PWA закрывает «десктоп + телефон» |
| Бэкенд | **Hono** на Bun | минимальный; переносим (Bun/Node/CF Workers); альтернатива — Elysia (bun-native), если переносимость не нужна |
| БД | **SQLite** (`bun:sqlite`) + Drizzle ORM | один файл, ноль администрирования; на клиенте кэш в IndexedDB |
| SRS | **ts-fsrs** | готовая реализация FSRS, не изобретать кривую забывания |
| Разговор | OpenAI Realtime (WebRTC) | см. выше |
| Drill-ASR | ~~Web Speech API~~ → распознавание с ограниченным словарём (Vosk в WASM); вариант B под вопросом | вариант A отклонён спайком №1 |
| VAD/латентность | @ricky0123/vad-web (Silero VAD, WASM) | замер времени реакции локально |
| Японский текст | wanakana (кана↔ромадзи), словарь JMdict | нечёткое сравнение ответов, словарная база |

Структура репозитория (набросок):

```
learn-japanese/
├── apps/
│   ├── web/        # React PWA: drill + разговорный UI
│   └── server/     # Hono на Bun: токены Realtime, SRS API, пуши
├── packages/
│   ├── core/       # типы, FSRS-обвязка, логика подбора карточек
│   └── jp/         # кана-таблицы, работа с чтениями, wanakana-утилиты
├── docs/
└── package.json    # bun workspaces
```
