# Спайк 1: мгновенное распознавание каны (Web Speech API)

Первый пункт плана из [TECH.md](./TECH.md): выяснить, годится ли встроенный
в браузер `SpeechRecognition` для drill-режима. Это go/no-go — от ответа
зависит, нужен ли платный ASR (вариант B) в MVP.

Код: [apps/web](../apps/web). Кроме этого спайка в репозитории пока ничего нет.

## Что именно измеряется

Транскрипт сваливает в одно число две совершенно разные величины, поэтому
спайк разделяет их:

| Метрика | Как измеряется | Что означает |
|---|---|---|
| **Начало речи** (onset) | локально, по энергии микрофона (Web Audio) | сколько человек вспоминал символ — метрика обучения, из неё потом делается оценка FSRS |
| **Задержка движка** (ASR lag) | момент совпадения минус onset | накладные расходы платформы — именно они решают судьбу варианта A |
| **Полная латентность** | от показа символа до совпадения | что чувствует пользователь |
| **Промахи** | гипотезы, которые не совпали и не являются началом верного ответа | точность движка на изолированных слогах |

Все гипотезы движка (включая промежуточные) пишутся в лог с таймингами —
в таблице результатов видно, что именно услышал движок на каждой карточке.

## Критерий go/no-go

Вариант A принимается, если на реальных прогонах (десктоп **и** телефон):

- медиана задержки движка ≤ **500 мс**;
- доля распознанных карточек ≥ **90 %** при **строгом** правиле совпадения.

Если не проходит — вариант A остаётся фолбэком, а основным для drill-режима
становится потоковая транскрипция OpenAI (вариант B). Интерфейс
`DrillRecognizer` ([recognizer.ts](../apps/web/src/lib/recognizer.ts)) для
этого и заведён: вторая реализация подставляется без переписывания дрилла.

## Как запустить

```bash
bun install
bun run dev
```

Открыть http://localhost:5173 в Chrome (десктоп) или Safari (macOS).
`localhost` — защищённый контекст, микрофон работает.

С телефона (LAN-адрес не является защищённым контекстом, поэтому нужен https):

```bash
bun run dev:https
```

Открыть `https://<IP-мака>:5173`, один раз принять самоподписанный
сертификат. Альтернатива — туннель (`cloudflared tunnel --url http://localhost:5173`).

Управление во время сессии: **Space** — пропустить карточку, **Esc** —
остановить.

## Мок-режим без микрофона

```
http://localhost:5173/?mock=1
```

Ответы вводятся с клавиатуры ромадзи. Нужен для проверки самого цикла дрилла
там, где микрофона нет (браузерные песочницы, CI), и как страховка от гниения
интерфейса `DrillRecognizer`. Задержка движка в мок-режиме нулевая по
построению, поэтому вердикт go/no-go в нём не считается.

## Как снять данные

1. Прогнать 20–40 карточек на **базовом наборе** каны, потом столько же
   с включёнными **ёон** (きゃ, しゅ…) — они самые опасные для распознавания.
2. Прогнать то же самое при **строгом** правиле совпадения: мягкое («содержит
   ответ») завышает точность, потому что засчитывает «ください» за «く».
3. Повторить на телефоне — движок и микрофон там другие.
4. Нажать «Скопировать JSON-отчёт» и приложить отчёт (в нём метрики, все
   гипотезы движка и user-agent) — по нему принимается решение.

## Что уже видно из кода, до замеров

- Ожидаемый ответ известен заранее, поэтому сравнение идёт не «что сказал
  человек», а «содержит ли гипотеза нужное чтение»: катакана, хирагана и
  ромадзи сводятся к одной форме через wanakana
  ([match.ts](../apps/web/src/lib/match.ts)).
- Распознавание запускается **один раз на всю сессию**, а между карточками
  меняется только ожидаемый ответ: старт распознавания на каждую карточку
  стоит слишком дорого для дрилла на скорость. Chrome сам обрывает сессию
  после тишины — она перезапускается автоматически.
- Мягкое правило совпадения оставлено для сравнения, но принимать решение
  нужно по строгому.

## Результат: **no-go**

Прогон 30 августа 2026, macOS, Chrome 151, 20 карточек базовой хираганы,
мягкое правило совпадения (то есть в пользу движка). Сырой отчёт:
[data/spike-asr-webspeech-macos-chrome151.json](data/spike-asr-webspeech-macos-chrome151.json).

| Метрика | Порог | Факт |
|---|---|---|
| Доля распознанных | ≥ 90 % | **5 %** (1 из 20) |
| Медиана задержки движка | ≤ 500 мс | 392 мс, но это **одно** измерение — величина бессмысленна |

Единственное «совпадение» — карточка け, на которой движок выдал «だけ»:
засчиталось только мягким правилом по подстроке. **По строгому правилу
результат 0 из 20.**

Важнее процентов то, *как* именно он провалился:

- **14 карточек из 20 — вообще ни одной гипотезы.** Движок не ошибся, он
  выбросил произнесённое как шум: одиночная мора короче минимальной единицы,
  которую он готов считать высказыванием.
- **На 5 карточках — подстановка реальных слов:** へ → «部屋», き → «コーヒー»,
  む → «冷え», り → «父» (и до этого «ち»), し → «G». Языковая модель тянет
  короткий звук к ближайшему словарному слову.

## Диагноз

Дело не в вендоре и не в настройках. Web Speech API — распознаватель
**слов**: у него есть языковая модель, эндпойнтинг и словарь, и все три
работают против нас. Мы же решаем принципиально другую задачу — **проверку
известного ответа**: ожидаемое чтение задано заранее, вопрос только
«произнёс ли человек именно это и как быстро».

Отсюда следствие, важное для выбора варианта B: **потоковая транскрипция
OpenAI — это тот же класс инструмента** (модель со словарём и языковой
моделью), и на изолированных морах у неё есть ровно те же основания
галлюцинировать слова. Платный ASR общего назначения не является
автоматическим решением этой проблемы, и переходить на него как на «более
качественный» — значит менять цену, не меняя природу инструмента.

Что из спайка **сработало** и остаётся в проекте:

- **Замер начала речи по энергии микрофона** — медиана 1614 мс, разброс
  336–2451 мс, значения правдоподобные. Это и есть метрика обучения
  (латентность припоминания), и она не зависит от того, каким движком мы
  потом сверяем ответ.
- Каркас замеров целиком: колода каны, сессия, лог гипотез с таймингами,
  отчёт, мок-режим. Следующий кандидат сравнивается по тем же числам.

## Дальше: сузить задачу, а не купить движок побольше

Кандидаты в спайк №2, в порядке приоритета:

1. **Распознавание с ограниченным словарём, локально.** Vosk (Kaldi) в
   WASM через `vosk-browser` умеет ограничивать распознавание списком слов:
   декодер обязан выбрать один из вариантов, и «部屋» просто неоткуда взять,
   если словарь — 46 мор. Японская модель `vosk-model-small-ja-0.22` весит
   48 МБ, Apache 2.0, работает офлайн и бесплатно.
2. **Оценка произношения по эталонному тексту (Azure Speech pronunciation
   assessment).** Инструмент правильного класса: на вход подаётся эталон,
   на выходе — оценки соответствия. Платный, облачный; в японском, по
   документации, пофонемные поля пустые, но послоговые оценки есть.
3. **Сменить единицу дрилла с моры на короткое слово.** Тогда работает
   любой обычный ASR, включая бесплатный Web Speech API. Это уже не
   технический выбор, а продуктовый: символ всё так же на экране, но
   произносится он в составе слова.
